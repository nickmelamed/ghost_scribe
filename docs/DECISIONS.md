# Decisions

Drafted from the code and its comments. Written plainly so you can edit
them into your own words. Each entry notes where it was seen.

## D1. Use the community DAIGT v2 dataset, not the official competition file
The official training set has no per-model generation-source labels, and
the project needs them to hold out a source. (`data/preprocess.py`,
`data/processed/dataset_summary.md`)

## D2. Treat generation source as a stand-in for time
There is no timestamp axis, so each generating model is a "batch". Two
sources are held out to mimic a new model appearing. This is a
substitution and must not be described as real drift. (`CLAUDE.md`,
`data/preprocess.py`)

## D3. Hold out falcon_180b_v1 and llama_70b_v1
Two sizeable, distinct model families, 1,055 and 1,172 rows.
(`HELD_OUT_SOURCES`)

## D4. Stratified 70/15/15 split by generation source, seed 42
So even the small sources appear in train, val, and test.
(`split_seen_pool`)

## D5. Classical features only in Stage 1, with a bigram-burstiness proxy
No LM perplexity, to keep Stage 1 cheap and fast. The proxy is documented
as an approximation. (`stage1/features.py`)

## D6. XGBoost is the Stage-1 decision model
Higher validation AUC than logistic regression (0.9930 vs 0.9837).
(`stage1/escalation_policy.py`, results)

## D7. Escalation bands set by percentile of distance from 0.5
Directly targets a 20% escalation rate instead of hoping fixed cutoffs
land in range. Calibrated on val. (`calibrate_bands`)

## D8. Two FPR variants for fairness
The 0.5-threshold FPR is comparable to the literature. The auto-flag-only
rate counts only people who would be flagged with no human in the loop,
which is the decision-relevant number for this tool. (`fairness/esl_eval.py`)

## D9. ELLIPSE as the ESL eval set
Real English Language Learner essays, not a proxy, but limited to US
grade 8-12 ELL students. The scope limit goes in the README.
(`fairness/data_prep_esl.py`)

## D10. Qwen2.5-3B-Instruct with LoRA, bf16 on MPS, no 4-bit
bitsandbytes does not support MPS and 64 GB memory fits a 3B model.
`requirements.txt` installs bitsandbytes on Linux only.
(`stage2/finetune_lora.py`)

## D11. Stage 2 fine-tunes on escalated cases only
Follows the CLAUDE.md rule. Rationales in the training target are
templated from real Stage-1 feature statistics, not generated by a model.
(`stage2/prepare_finetune_data.py`)

## D12. Asymmetric review queue
"AI-generated" verdicts always go to a human. Confident "Human-written"
verdicts may skip review, since clearing takes no action against a
student. This keeps a human on every accusatory path.
(`stage2/build_review_queue.py`, `stage2/confidence.py`)

## D13. Human-gate rate of 20%, calibrated on the escalated test split
The lowest-confidence dangerous error (predicted human, actually AI) sat
at the 16th percentile, so 20% adds margin. This uses test-split errors to
set a parameter, which conflicts with keeping test untouched.
**Status: marked for change.** To be recalibrated on val, see SPEC 6.1.

## D14. Review queue comes from the val split
Keeps the test split clean for evaluation. (`hitl/review_app.py`)

## D15. Reviewers never see ground truth
Labels are dropped before display, so reviews are blind like a real
deployment. (`hitl/review_app.py`, `hitl/llm_review.py`)

## D16. LLM reviewer uses the base model, kept in a separate file
Using the fine-tuned model would be close to grading its own work. LLM
reviews are never merged with human reviews, so a round trained on each
can be compared. (`hitl/llm_review.py`, `hitl/apply_corrections.py`)

## D17. Corrections use the reviewer's label
Not Stage 2's suggestion and not ground truth. (`hitl/apply_corrections.py`)

## D18. Unparseable Stage-2 output falls back to Stage 1 and is counted
Fallbacks are logged in the results table, not silently dropped.
(`results/metrics_comparison.md`)

## D19. Raw data, processed splits, adapters, and reviews stay out of git
These are gitignored, and `data/download.py` documents how to fetch the data. The
results cannot be reproduced from the repo alone.
